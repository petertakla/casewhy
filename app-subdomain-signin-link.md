# New task for Claude Code — give the app a real subdomain, link "Sign in" from the static site

**Decided, Sep 6 (cloud session):** production setup is the standard split — `casewhy.com` (root) stays the static marketing/waitlist site, the live product moves to `app.casewhy.com`. This came out of Peter asking how to sign in from the static page and finding there's currently no link at all between the two — the static site (still its pre-launch "Coming soon" waitlist page) has zero nav link to the app, and the app itself is only reachable today at the raw `casewhy-app.vercel.app` URL. Confirmed by fetching both live: `casewhy.com`'s only interactive elements are its two "Notify me at launch" email-capture forms; `casewhy-app.vercel.app/auth/sign-in` is a real, working magic-link sign-in form. `app.casewhy.com` doesn't currently resolve (no DNS record yet).

## Why the subdomain split, not just linking to the `.vercel.app` URL directly

Putting a raw `casewhy-app.vercel.app` link on the production marketing site is fine for internal testing but not for a real launch — it looks unfinished/untrustworthy on a page meant to build trust with USCIS applicants handling sensitive case data, and it locks the app's public identity to a Vercel-assigned URL that never changes. A subdomain (`app.casewhy.com`) is the fix, and it also mirrors the split that already exists in this repo between the static site and the Next.js app (separate branches, separate deployments) — this just makes that split visible in the URL structure instead of papering over it with a single confusing entry point.

## What needs to happen (two parts — DNS/hosting config, then one code change)

1. **Add `app.casewhy.com` as a custom domain on the Next.js app's Vercel project**, pointed at the same deployment currently live at `casewhy-app.vercel.app`. This is a Vercel project-settings action (add domain → Vercel gives back the DNS record to create) — Claude Code has already done Vercel-side actions in this project before (round 13: added env vars and triggered a prod redeploy, both confirmed with Peter first), so the same access likely covers this, but it should still be confirmed with Peter before touching production domain config, same as the round-13 precedent.
2. **Add the actual DNS record** (a CNAME, per whatever Vercel's domain-setup step specifies) wherever `casewhy.com`'s DNS is actually hosted (registrar or a service like Cloudflare) — this is very likely a Peter-only step unless Claude Code already has credentials to that specific DNS provider, which hasn't come up before in this project. Flag plainly rather than guess at access here.
3. **Add a real "Sign in" link to the static site's nav** (`casewhy.com`, the `main`-branch static site), pointing at `https://app.casewhy.com/auth/sign-in` — a small, low-risk code/content change, safe to build in parallel with steps 1-2 rather than waiting on DNS to actually propagate first (the link just won't resolve correctly until the domain is live).
4. **Once `app.casewhy.com` resolves, double-check nothing in the Next.js app hardcodes `casewhy-app.vercel.app`** (redirect URLs, CORS/auth allowed-origins config, the Stripe Checkout success/cancel URLs from round 13, the email-notification links from Postmark) — these should already be built off an env var or relative paths per normal practice, but worth a real check rather than assuming, since a hardcoded old URL would quietly break sign-in links sent by email or the post-checkout redirect.

## Sequencing

Not urgent/blocking — this can slot in whenever, doesn't gate anything else in flight (round 13's business-prerequisite chain, round 14's `/news` follow-up). Worth doing before real users start signing up, though, since right now there is no way for a visitor to get from the marketing site into the actual product at all.
