# CaseWhy — Technical Brief for USCIS Production API Access

Prepared for USCIS Torch Developer Support ahead of the Case Status API production-access demo. Version 2, September 16, 2026.

**Primary contact:** as listed on the production-access attestation. **Applicant:** CaseWhy LLC (Florida).

**What CaseWhy is:** a free web application that lets people track the status of their own USCIS case by receipt number, explains what a status means in plain language, and shows published processing times and Visa Bulletin data. It is not a law firm and gives no legal advice. Live at `app.casewhy.com`.

**Demo environment:** the live demo runs on a dedicated account using sandbox test receipt numbers only — no real personally identifiable information appears on screen at any point. In production, the same code path applies to real receipt numbers, and the app enforces its own internal daily and per-second call caps regardless of whatever quota USCIS ultimately grants (see "Rate limiting and volume").

A `demo_id` header, assigned by USCIS, is sent on every Case Status API request while the demo is active (`src/lib/uscis/client.ts`, `demoIdHeader()`).

File upload / encoded-document handling is a FOIA API criterion, not a Case Status API one, and is out of scope for this demo.

## 1. Data entry usability

The receipt-number field gives real-time format feedback as the user types (3 letters followed by 10 digits), with clear error copy, without ever blocking submission — a well-formed number still might not correspond to a real case.[^1] The app supports English and Spanish throughout, is fully responsive on mobile, and a new user can sign up and track their first case in under two minutes.

## 2. JSON payload conversion

`getCaseStatus()` builds the outbound request to USCIS's Case Status API from the entered receipt number.[^2] The exact request that will be sent — method, URL, and headers, with the access token redacted — is visible in the dashboard via a "Show technical details" toggle on the on-demand check button, generated by the same function that makes the real call, not a separate description.[^3]

## 3. OAuth 2.0 authentication

CaseWhy uses the OAuth 2.0 Client Credentials grant.[^4] `getAccessToken()` requests a token from USCIS's token endpoint using the client ID and secret, and caches it in memory, refreshing automatically shortly before expiry rather than on every call.[^5] Sandbox and production use separate credential pairs and separate token/API base URLs, selected by a single environment variable — there is no code path where they can be mixed up.[^6] Credentials are read from environment variables, never committed to source control, and live only as encrypted environment variables in Vercel.

The USCIS API client runs exclusively on the server. **Client ID, client secret, and access tokens never reach the browser** — the browser only ever talks to CaseWhy's own server, which in turn talks to USCIS.[^7]

## 4. HTTPS response handling — every documented response code

Every response from USCIS's API — success or error — is handled by the same code path (`uscisRequest()` → `UscisApiError` → `extractUscisErrorMessage()`) and its message reaches the interface directly.[^8] There is no automatic retry logic and no per-code special-casing that could silently diverge from this path.

| Code | Meaning | Tested how | What the user sees |
|---|---|---|---|
| 200 | Success | Live, routinely (see "Sandbox testing") | Status text, description, and history rendered in the dashboard. |
| 422 | Malformed receipt number | Live, real sandbox response | USCIS's own message, shown directly (confirmed: *"The application receipt number is not formatted correctly..."*). |
| 404 | Unrecognized receipt number | Live, real sandbox response | USCIS's own message, shown directly (confirmed: *"Case Status Online does not recognize the receipt number entered..."*). |
| 429 | Rate limit exceeded | Live — occurred once during the sandbox volume test (one call out of 50 in a single batch, Sep 15) | USCIS's own message, shown directly through the same path as 422/404; the very next scheduled batch completed cleanly. Now additionally guarded against before the call is even made — see "Rate limiting and volume." |
| 401 | Authentication failure | Same code path as every other non-2xx response; not independently triggered against this project's own live credentials, since deliberately invalidating a working credential to force a real 401 risks disrupting the in-progress sandbox test window | Same uniform error-message display. |
| 403 | Forbidden | Not documented as a Case Status response for this integration; same uniform path would handle it if USCIS ever returns one | Same uniform error-message display. |
| 500 / 503 | Server error | Not independently reproducible against a live third-party system; same uniform path applies | Same uniform error-message display. |
| Timeout / no response | Network failure or a hung request | A 15-second client-side timeout was added specifically for this demo (previously, a request had no timeout at all) — code-reviewed, not yet observed live since USCIS's sandbox has not hung during testing | Same uniform error-message display: "Request to USCIS timed out after 15 seconds." |

Receipt numbers are never written to logs in plaintext, for any response code.

## 5. Case status tracking

A tracked case stores an encrypted receipt number, case type, and last known status; `case_status_history` stores one row per USCIS history entry (service-center prefix only, never the full receipt number).[^9] The scheduled status-check job compares the freshly fetched status against the last known one and — only on a genuine change, never on the first check — sends a Postmark email and, if enabled, a push notification.[^10]

Adding a case is a short signed-in flow; removing one is immediate and self-serve (`untrackCase()`, a real, ownership-checked delete).[^11] Free accounts can track up to 3 cases; the paid tier raises this in tiers up to a hard ceiling.[^12]

# Additional Technical & Operational Detail

## Architecture and hosting

CaseWhy is a Next.js 15 application (App Router) hosted on Vercel, with PostgreSQL (Neon) for data storage via Drizzle ORM.[^13] Transactional email runs through Postmark; billing (for the optional paid tier) through Stripe. Every server route runs on Vercel's standard Node.js runtime, chosen specifically because the app's database access needs a real TCP connection pool, which the Edge runtime doesn't support.[^14] There is no native mobile app; CaseWhy is an installable Progressive Web App.

## File upload (document vault)

Not a Case Status API criterion — a FOIA API criterion, out of scope for this demo, included here for completeness. The paid tier includes a working document-upload feature: PDF, JPEG, or PNG up to 10 MB, stored in Vercel Blob under private access (never a public URL), with the original filename encrypted before storage.[^15] Downloads are proxied through CaseWhy's own server rather than exposing a direct Blob URL.[^16] No uploaded document is ever sent to USCIS or any third party.

## Rate limiting and volume

The client enforces a real, hard cap before any call is made: no more than 1,000 Case Status API calls per calendar day and no more than 4 in any rolling one-second window, checked against a call log before each request and refusing (with a logged event) if either would be exceeded.[^17] These thresholds are set at the sandbox's own confirmed limits (5 TPS, 1,000/day) rather than an unverified production number — USCIS's own production quota is shared once access is granted, and the caps are configurable to raise once that figure is known.

On top of that hard floor, the schedule paces volume naturally: the production status-check job runs on a fixed schedule per tracked case, and an on-demand check is a paid-tier feature rate-limited by real human clicks — volume scales linearly and predictably with the number of tracked cases, not with traffic spikes. Expected volume at launch: on the order of tens of calls per day (one scheduled check per active tracked case); growth tracks user adoption directly, with the hard cap above as the actual ceiling regardless of how many users sign up.

A separate example of the team's general rate-limiting practice: the anonymous "ask a question" feature enforces a durable, database-backed lifetime cap per IP address.[^18]

## Privacy, security, and data handling

Receipt numbers are treated as personally identifiable information: encrypted with AES-256-GCM before being written to the database, with the encryption key held separately from the database itself.[^19] No CaseWhy staff member can view a receipt number in plaintext through any administrative tool.

What is sent to the AI service (Claude, via Anthropic, through the Vercel AI Gateway): form type, processing center, dates, status text/description, full status history, and matched policy background. **The raw receipt number is never included**, by design in the prompt-construction code.[^20] The one exception: the paid-tier escalation-letter drafting tool includes the receipt number in the drafted letter itself, since the letter has to identify the case to USCIS or a congressional office; this exception is disclosed in the Privacy Policy alongside the general rule.[^21]

Third parties that receive any case- or account-related data, and what each receives: **Anthropic** (status text, dates, and history for AI explanations; additionally the receipt number when drafting an escalation letter, as above), **Postmark** (the notification email address and status text, to send account and status-change emails), **Vercel** and **Neon** (infrastructure — hosting and database, with no independent access to decrypted data outside the app's own code), and **Stripe** (billing information for the optional paid tier only, not case data). Each is contractually and/or technically limited to using data only for the relevant part of the service.[^22]

Authentication is via Neon Auth, supporting both password and magic-link sign-in.[^23] Admin access is gated by a single allow-listed email, fail-closed if unset.[^24]

Removing an individual tracked case is immediate and self-serve. Full account deletion is a request to `privacy@casewhy.com`, completed within 30 days.[^25] Users are required to actively acknowledge a material change to the Privacy Policy or Terms of Use the next time they sign in, not just notified by email.[^26]

Security headers — HSTS, a Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, and Referrer-Policy — are set on every response.[^27] Automated dependency-update monitoring runs via Dependabot, with `npm audit` also surfaced in CI; two pre-existing transitive dev-tooling findings (not runtime-reachable application code) are open pending a deliberate major-version upgrade, tracked rather than silently ignored.[^28]

## Business and operations

A free tier (3 tracked cases, 3 AI questions/month, full access to all reference data) and a paid "Plus" tier ($9.99/month, $39.99/6 months, or $69.99/year).[^29] **Nothing from the USCIS Case Status API is ever paywalled** — status checking is free at every tier; Plus adds more tracked cases, unlimited AI questions, on-demand checks, the document vault, and drafting tools. Billing runs on Stripe, currently in test mode — CaseWhy has processed no real production payments to date.[^30]

Support runs through 13 real, monitored email aliases on the domain, including `security@`, `privacy@`, `legal@`, and `abuse@`.[^31] If production API access were ever revoked, CaseWhy has no scraping fallback and would show an honest degraded-service message rather than attempt an unauthorized alternative path to USCIS data.

## Sandbox testing

CaseWhy is running a dedicated 5-business-day sandbox volume test, September 14–18, 2026, using the app's real production code path, not a mock.[^32] Each run draws from a confirmed pool of real sandbox test receipt numbers spanning 7 form types, at roughly 50 calls per run (a mix of successful and deliberate-error lookups), 18 runs/day across the sandbox's 7 AM–8 PM ET operating hours — roughly 900 calls/day, under the sandbox's published 1,000-request/day, 5-transactions-per-second ceiling.

Results are reported honestly, including the one real anomaly observed: Monday (Sep 14) ran clean throughout. Tuesday (Sep 15) completed 15 runs, ~750 calls, with one batch returning a single real `429` (rate-limit) response — the very next scheduled batch completed with no issue, and no other run that day or since has repeated it. Wednesday (Sep 16, in progress at the time of writing) has completed 11 runs, ~550 calls, cleanly. Thursday and Friday (Sep 17–18) complete the window; final totals will be provided once available.
