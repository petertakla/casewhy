# New task for Claude Code — round 62: nav shows "Sign out" (and the full signed-in menu) while Peter believes he's signed out

**Status: authorized now, Sep 10 — real bug report with a screenshot, found while trying the new `/get-help/ask` page from round 60.** Peter, verbatim: "I'm not sogned-in but menu says sign-out. menu should be state aware." Screenshot shows `app.casewhy.com/get-help/ask` (in what looks like an in-app/PWA browser view) with the full signed-in nav bar (Dashboard, Ask a question, CaseWhy Plus, Get Help) and "Sign out" in the top right — the exact render path `AuthHeader.tsx` only takes when `isSignedIn` is true.

## What I checked before writing this — and why I'm not prescribing the fix

Read `src/components/AuthHeader.tsx` directly. On its face the code already does the right thing: `const isSignedIn = !isPending && !!session?.user;`, gates both the nav links and the Sign in/Sign out block on that, and has an explicit comment about exactly this class of bug ("a signed-out visitor landing on one of those must never see the signed-in-only links"). So this isn't an obviously-missing state check in the component itself — which means guessing the cause from here would repeat the round 57 mistake (leading with a hypothesis instead of the real cause). Three real possibilities, roughly in order of how concerning they'd be, and this task is to find out which one it actually is:

1. **A genuinely valid, lingering session cookie on the device Peter tested from.** If real end-to-end testing happened on this device/browser earlier (round 52's "real disposable account," or any other round's live verification), a session cookie could still be active — in which case the header is *correctly* reporting a real signed-in state, and "not signed in" was Peter's own mistaken assumption, not a bug. Check this first: does the request that hit `/get-help/ask` in the screenshot actually carry a valid session cookie/token server-side for a real account?
2. **A stale service worker / PWA cache** (`ServiceWorkerRegister.tsx` is registered app-wide) serving an old cached shell from a moment when a session was active, or an old JS bundle, rather than the current `AuthHeader` logic. The screenshot's browser chrome (an "X" close button, no normal tab bar) suggests this may have been opened via a link/share-sheet in an in-app or PWA-style view, which is exactly the kind of context that can serve a cached shell longer than a normal tab.
3. **A real bug in how `authClient.useSession()` resolves** — e.g., the session-check endpoint or its response getting cached somewhere (CDN, edge, or client-side) in a way that could serve one browser's earlier session state to a later, actually-signed-out request. This is the possibility to take most seriously: if it's this, it's not just a nav cosmetic issue, it's a session-handling bug worth understanding fully before ruling out anything more serious (like a cached response being shared across different browsers/devices, not just replayed on the same one).

## What to do

Reproduce for real — genuinely signed out (fresh incognito/private window, cookies cleared, not just "logged out UI state") — and confirm what `authClient.useSession()` actually returns at `/get-help/ask` and at a couple of other pages for comparison. If it's (1), no code changes: just confirm Peter's account was in fact still signed in on that device, and say so plainly — an honest "not a bug" is as valid a finding as a real one, same as round 55. If it's (2) or (3), find the actual mechanism (don't stop at "seems cache-related" — trace it to the actual cached response or actual endpoint behavior) and fix that, not just the symptom.

## Verify live

Confirm a genuinely fresh, cookie-cleared, signed-out session shows "Sign in" and the signed-out nav (not the full menu) on `/get-help/ask` and at least one other page, and that a real signed-in session still correctly shows "Sign out" and the full nav — both directions, not just the one that was broken. If a caching layer was involved, confirm the fix holds across a second fresh signed-out load, not just once. `tsc`/lint clean, production build succeeds. Report back the actual root cause found (not the leading hypothesis) and fold into `CLOUD_CLAUDE.md`'s standing status.
